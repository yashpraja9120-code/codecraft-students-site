Git and GitHub Basics Every Student Should Know

The handful of Git commands that cover 95% of real student work, plus a mental model for what's actually happening under the hood.

2026-02-14 · 7 min read · git, tools

What Git actually is

Git is a version control system: it keeps a history of every saved change to your project, so you can go back to an earlier version, see exactly what changed and when, and work on features without risking your main, working code. GitHub is a separate thing — a website that hosts Git repositories online so you can back them up and collaborate with others.

The mental model that makes Git click

Git tracks snapshots, not files. Every time you "commit," Git saves a snapshot of your entire project at that moment and gives it a unique ID. Your project's history is just a chain of these snapshots, and most Git commands are really about moving between them or combining them.

The commands that cover almost everything

# One-time setup for a new project
git init

# Check what's changed
git status

# Stage specific changes for the next commit
git add filename.py
git add .            # stage everything changed

# Save a snapshot with a message
git commit -m "Add temperature converter function"

# See the project history
git log --oneline

# Connect to a GitHub repository and push your history
git remote add origin https://github.com/username/repo.git
git push -u origin main

# Get someone else's latest changes
git pull

Branches, without the confusion

A branch is just an independent line of history. The default branch (usually main) holds your stable code; creating a new branch lets you experiment or build a feature without touching it.

git branch feature-login       # create a branch
git checkout feature-login     # switch to it
git checkout -b feature-login  # do both in one step

# once the feature works, merge it back
git checkout main
git merge feature-login

A workflow you can actually follow

  1. Pull the latest changes before you start working: git pull.
  2. Create a branch for whatever you're about to build.
  3. Commit small, focused changes with clear messages as you go — not one giant commit at the end.
  4. Push the branch and open a pull request on GitHub if you're working with others.
  5. Merge once it's reviewed (or once you're satisfied, if it's a solo project).
Common trapA vague commit message like "fixed stuff" is useless six weeks later. Write commit messages that describe what changed and why, as if explaining it to a teammate who wasn't there.

When something goes wrong

git status is your first move in almost every confusing situation — it tells you exactly what state your files are in relative to your last commit. From there, git log shows you the history, and git diff shows exactly what changed, line by line, before you commit it.
